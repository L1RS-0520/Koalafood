# 考拉食堂 · 照片存储方案对比（KV / D1 / R2）

日期：2026-11-09　作者：羊驼后端组长　状态：**码驼已定默认用 Workers KV，R2 只作备选**；上线用哪个最终由大王拍板（见 `../../待大王审批.md`）。
数字全部来自 Cloudflare 官方文档（2026-11-09 查阅，页面标注 “Last updated Oct 30, 2026”），出处见文末。
容量口径按码驼要求一律 **1024 进制**：1 GB = 1,073,741,824 字节；950MB = 996,147,200 字节；500KB = 512,000 字节；1MB = 1,048,576 字节。

## 1. 一句话结论

| 方案 | 要不要绑卡 | 超额会怎样 | 能存多少道菜（单张 500KB，每道 3 张 / 9 张） | 推荐 |
|---|---|---|---|---|
| **Workers KV**（默认） | **不用**（Workers 免费版自带） | **直接报错，不扣费** | 按 950MB 安全上限：约 **648 道 / 216 道** | ✅ 上线默认 |
| D1（照片 BLOB 存进数据库） | 不用 | 直接报错，不扣费 | 单库 500MB：约 341 道 / 113 道（还会挤占菜谱数据的空间） | 不推荐，仅保底 |
| R2 | **要**（开通需走结账流程、绑付款方式） | **超免费额度按量扣费** | 10 GB：约 6,990 道 / 2,330 道 | 备选，大王愿意绑卡再切 |

大王的规矩是“要花钱的直接跳过”，所以选 **不绑卡、超额只报错** 的 KV；容量对一个人记菜谱足够用几年。

## 2. Workers KV（默认，`PHOTO_STORE=kv`）

| 项目 | 免费版 | 出处 |
|---|---|---|
| 是否要绑卡 | 不用。KV 包含在 Workers Free 计划里 | [1][2] |
| 存储容量 | 1 GB / 账户（每个 namespace 也是 1 GB） | [1][2] |
| 单个值上限 | 25 MiB（键 512 字节，metadata 1024 字节） | [1] |
| 读取 | 100,000 次 / 天 | [1][2] |
| 写入（不同键） | 1,000 次 / 天 | [1][2] |
| 删除 | 1,000 次 / 天 | [2] |
| list | 1,000 次 / 天 | [2] |
| 同一个键 | 每秒最多写 1 次，超了抛 429 | [1][3] |
| 重置时间 | 每天 00:00 UTC | [2] |
| **超额后** | “If you exceed any one of these limits, further operations of that type will fail with an error.”——**该类操作直接报错，不扣费**；读不受写额度影响 | [2] |
| 一致性 | 最终一致：写入在同一个机房立即可见，其他机房最多约 60 秒才可见 | [3][4] |

**容量估算**（后端安全上限 `STORAGE_LIMIT_BYTES` 默认 950MB = 996,147,200 字节，给 1 GB 留 5% 余量）：

| 单张大小 | 能存照片 | 每道 3 张 | 每道 9 张（最多） |
|---|---|---|---|
| 500KB（512,000 字节，前端压缩后的典型值） | 1,945 张 | **648 道** | **216 道** |
| 1MB（1,048,576 字节，后端单张上限） | 950 张 | 316 道 | 105 道 |

**每天写入上限对上传的影响**：
- 官方是写入 1,000 次/天、删除 1,000 次/天分开算。后端为了保守，把 **put 和 delete 合并计数**，上限 `KV_DAILY_WRITE_LIMIT=1000`（D1 表 `kv_usage`，按 UTC 日期）。
- 每传 1 张照片 = 1 次写入；删 1 张 = 1 次。所以**每天最多传约 1,000 张**：每道 3 张约 **333 道**，每道 9 张约 **111 道**；如果当天还删了照片，按删掉的张数相应减少（换一张照片 = 删 1 + 写 1 = 2 次）。
- 大王一天记几道菜，远远用不完。真正可能撞线的是一次性搬家/批量导入（例如从 R2 迁移 2,000 张要分 2 天以上）。
- 撞线时：上传返回 429 `STORAGE_QUOTA`「今天食堂的照片柜塞满啦，明天再来传吧～」，一张都不写、不留半条菜；浏览照常；删除照常成功，KV 删不了的记进 `orphan_photos`，第二天有写入时自动清理。

**读取**：每看一张照片 = 1 次 KV 读 + 1 次 D1 读（确认照片仍登记在册）。照片响应带 `Cache-Control: public, max-age=31536000, immutable`，同一浏览器看过就不再请求。100,000 次/天对个人站绰绰有余（Workers 免费版本身也是 100,000 次请求/天 [6]）。

优点：不绑卡、超额只报错不扣费；单值 25 MiB 远大于 1MB；读快（边缘缓存）；与 Worker 同账户免配置。
缺点：总容量只有 1 GB；每天 1,000 次写入；最终一致（刚上传的照片在别的机房可能最多约 60 秒看不到，同一机房立即可见）；没有“按前缀批量删”的便宜办法。

## 3. D1（`PHOTO_STORE=d1`，照片存 `photo_blobs` 表）

| 项目 | 免费版 | 出处 |
|---|---|---|
| 是否要绑卡 | 不用 | [5] |
| 存储容量 | 单库 500 MB，账户合计 5 GB，最多 10 个库 | [5][7] |
| 单行 / BLOB 上限 | 2,000,000 字节（所以后端单张上限 1MB 才放得下） | [7] |
| 读 | 500 万行 / 天 | [5] |
| 写 | 10 万行 / 天 | [5] |
| 重置时间 | 每天 00:00 UTC | [5] |
| **超额后** | “D1 API will return errors to your client indicating that your daily limits have been exceeded.”——**报错不扣费**；容量满了要删数据 | [5] |

容量估算（照片和菜谱共用 500MB = 524,288,000 字节）：500KB 一张约 1,024 张 → 每道 3 张约 **341 道**，9 张约 **113 道**。
优点：不绑卡；强一致；照片和数据一起备份（Time Travel 7 天）；写入额度宽（10 万行/天）。
缺点：容量最小；**照片把库撑满后，连文字菜谱都写不进去**；大 BLOB 让查询和备份变慢。可以单独建一个“照片库”缓解（免费版最多 10 个库），但这次不做。

## 4. R2（`PHOTO_STORE=r2`，只在 `wrangler dev --env r2` 下可用）

| 项目 | 免费额度（每月） | 出处 |
|---|---|---|
| 是否要绑卡 | **要**：需先在控制台完成 R2 订阅的结账流程（绑定付款方式）才能用 | [8][9] |
| 存储 | 10 GB-month | [9] |
| Class A（写、list） | 100 万次 / 月 | [9] |
| Class B（读） | 1,000 万次 / 月 | [9] |
| 删除 | 免费 | [9] |
| 出口流量 | 免费 | [9] |
| 单对象上限 | 约 5 TiB（单次上传 5 GiB） | [10] |
| **超额后** | **按量计费**：存储 $0.015/GB-月、Class A $4.50/百万次、Class B $0.36/百万次 | [9] |

容量估算（10 GB = 10,737,418,240 字节）：500KB 一张约 20,971 张 → 每道 3 张约 **6,990 道**，9 张约 **2,330 道**。
优点：容量大、写入额度宽、强一致、是存图片的“正统”方案。
缺点：**要绑卡，超额会自动扣费**，违反大王“花钱的直接跳过”的规矩。

## 5. 推荐与切换

- **推荐上线用 KV（默认）**：免费、不绑卡、超额只报错；后端已做 950MB 容量上限（507）和每天 1,000 次计数（429），在撞到官方限制前先拦住。
- 存满或嫌少时：①先删旧照片；②大王同意绑卡后切 R2（改 `PHOTO_STORE=r2` + 加 R2 绑定，用 `scripts/migrate-photos --from kv --to r2` 迁移）。
- 切换不影响接口和照片地址（都是 `/api/photos/<key>`）。
- 最终用哪个，由大王决定（已写进待审批）。
