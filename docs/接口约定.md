## 目录分工
- `worker/`：后端（Cloudflare Worker + D1 + 照片存储 KV/R2/D1 三选一，默认 KV），后端组负责
- `web/`：前端，前端组负责；构建产物放 `web/dist/`
- `docs/`：约定文档，两边都可改
- 本地联调：在 `worker/` 运行 `npx wrangler dev`，端口 8787。Worker 同时用 assets 托管 `../web/dist`，所以 `http://localhost:8787/` 是前端，`/api/*` 是接口，同源，无跨域。前端自己开 dev server 时把 `/api` 代理到 8787 即可（开发期后端也放开 CORS）。

## 通用约定
- 所有接口前缀 `/api`，JSON 用 UTF-8，字段名小写下划线。
- 成功：HTTP 200/201，直接返回数据对象。
- 失败：HTTP 4xx/5xx，返回 `{"error":{"code":"字符串","message":"给大王看的中文提示"}}`。前端直接显示 message。
- 常见 code：见文末 v2.1 错误码（v1 的 AI 相关错误码已去掉）。
- 时间为 ISO 8601（UTC）。
- 登录：线上由 Cloudflare Access 挡在外面，接口本身不做登录；本地无登录。

## 分类（固定）
`GET /api/categories` → `{"categories":["家常菜","汤羹","主食","小吃点心","甜品饮品","其他"]}`

## 菜品对象 Dish
```json
{
  "id": "uuid",
  "name": "番茄炒蛋",
  "category": "家常菜",
  "note": "少放糖",              // 可为 null
  "photo_url": "/api/photos/<key>",
  "ingredients": [ {"name":"鸡蛋","amount":"3个"} ],
  "steps": [ {"text":"鸡蛋打入碗中，加 1 克盐，用筷子打散约 30 秒至起泡","heat":"","time":"30秒","caption":"打散它！"} ],
  "tips": ["番茄选熟透的更出汁"],       // 可为空数组
  "servings": "2人份",                 // 可为 null
  "total_time": "15分钟",              // 可为 null
  "ai_status": "pending | done | failed",
  "ai_error": null,                    // failed 时为中文原因
  "created_at": "...", "updated_at": "..."
}
```
- steps 每项：`text` 必有（完整一句，包含用量/火候/时间）；`heat`（火候，如“中火”，可为空串）、`time`（如“2分钟”，可为空串）方便前端做漫画小标签；`caption`（可选，≤12 字，漫画格对白，如“下锅！”，可为空串，mock/real 都生成）。
- 列表接口返回精简版 DishSummary：`id,name,category,photo_url,ai_status,created_at`。

## 接口
| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/dishes?category=家常菜` | 列表，按 created_at 倒序；不传或 `全部` 返回全部。→ `{"dishes":[DishSummary]}` |
| POST | `/api/dishes` | 上传。`multipart/form-data`：`name`(必,≤30字) `category`(必) `photo`(必,jpg/png/webp,≤10MB) `note`(可,≤200字)。**同步生成**：返回时已生成完（ai_status=done），或生成失败（ai_status=failed，菜名照片已保存）。→ 201 `Dish`。前端在请求期间显示加载动画（目标 30 秒内）。 |
| GET | `/api/dishes/:id` | 详情 → `Dish` |
| PATCH | `/api/dishes/:id` | 编辑文字字段，JSON：可含 `name category note ingredients steps tips servings total_time`，只改传了的 → `Dish` |
| PUT | `/api/dishes/:id/photo` | 换照片，`multipart/form-data` 的 `photo`，旧图从 R2 删除 → `Dish` |
| POST | `/api/dishes/:id/regenerate` | 重新生成食材/步骤，覆盖旧的（确认弹窗由前端做）。可选 JSON `{"note":"这次加了土豆"}` 更新备注后再生成 → `Dish` |
| DELETE | `/api/dishes/:id` | 删除，同时删 R2 照片 → `{"ok":true}` |
| GET | `/api/photos/:key` | 读照片（Worker 从 R2 读，桶不公开），带 Content-Type 和缓存头 |
| GET | `/api/health` | 见 v2.1：`{ok, chef_enabled, chef_pending}` |

### Dish 字段变化
- `source`: `chef | manual`（厨驼写的、或大王手写/编辑过仍保留原来源；大王编辑 chef 菜谱后 source 不变）。
- `chef_status`: `none | pending | done`（none=手写没找厨驼；pending=待写，前端显示“厨驼正在写菜谱…”；done=厨驼已交稿）。替代 `ai_status`。
- `chef_requested_at`、`chef_done_at`：ISO 或 null。
- ingredients/steps 允许空数组，amount 允许空串；steps 项仍为 `{text, heat, time, caption}`。
- DishSummary 加 `chef_status`、`source`。

### 大王侧接口（前端用）
| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/dishes` | multipart：`name category photo note` + `mode=chef|manual`。`chef`：只存菜名/照片/备注，chef_status=pending，source=chef，食材步骤为空。`manual`：可带 `ingredients steps tips`（JSON 字符串）`servings total_time`，可全空只写 note，source=manual，chef_status=none。→ 201 Dish |
| POST | `/api/dishes/:id/ask-chef` | 让厨驼（重）写，可选 JSON `{"note":"..."}`。置 pending；旧食材步骤保留到厨驼交稿时才覆盖（前端先弹确认）。→ Dish。厨驼关闭时 403 `CHEF_DISABLED` |
| GET | `/api/settings` / PATCH 同 | `{"chef_enabled":true}`，存 D1 `settings(key,value)`。关闭后 mode=chef 和 ask-chef 返回 403 `CHEF_DISABLED`，前端隐藏“找厨驼写” |
| GET | `/api/health` | `{"ok":true,"chef_enabled":true,"chef_pending":2}` |
其余（列表/详情/PATCH/换图/删除/照片）不变；`/regenerate` 由 `ask-chef` 替代。前端对 pending 菜品轮询 `GET /api/dishes/:id`（建议 10 秒一次）。

### 厨驼侧接口（需请求头 `X-Chef-Key`，值=Worker secret `CHEF_KEY`，本地放 `worker/.dev.vars`，不进 git；错了返回 401 `UNAUTHORIZED`）
| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/chef/tasks` | 待写列表（chef_status=pending，按请求时间正序）→ `{"tasks":[{id,name,category,note,photo_url,requested_at,claimed_at}]}` |
| POST | `/api/chef/tasks/:id/claim` | 领取（记 claimed_at，防重复写；已被领 30 分钟内再领返回 409 `CONFLICT`，超时可重领）→ task |
| POST | `/api/chef/tasks/:id/draft` | 交稿 JSON `{ingredients, steps, tips?, servings?, total_time?}`，经统一 `normalizeDraft` 校验（食材每项 name 必有；步骤 1–20 步、text 必有；caption 截断 12 字）。通过后写入菜品，chef_status=done，source=chef。非 pending 返回 409；格式错 400 `VALIDATION`（message 说明哪里不对）→ Dish |

### 错误码（v2）
`VALIDATION` 400 · `UNAUTHORIZED` 401 · `CHEF_DISABLED` 403 · `NOT_FOUND` 404 · `CONFLICT` 409 · `TOO_LARGE` 413 · `BAD_TYPE` 415 · `INTERNAL` 500

### 生成器结构
保留统一的“草稿来源”抽象：`RecipeDraft` 类型 + `normalizeDraft()`；现在唯一来源是厨驼交稿接口，以后换别的来源只加一个实现，不改路由。

## v2.1 最终定稿（后端组长 23:00）——唯一准绳，覆盖上面 v2 和 docs/接口约定-v2-厨驼.md 的冲突处

- `source`: `chef | manual`（正式内容来源）。`draft`：仅 draft 状态非空，`{ingredients, steps, tips, servings, total_time, chef_message}`。正式内容在顶层，重写期间旧内容照常显示。`requested_note`：大王给厨驼的要求。`chef_requested_at`。

  - `POST /:id/confirm`（可带修改后的内容；不带用草稿原样）→confirmed，source=chef，清空 draft
  - `POST /:id/discard-draft`→confirmed（正式内容不变，可能为空）
  - `PATCH /:id` 编辑正式内容→confirmed，source=manual，并作废未处理的厨驼任务（pending/draft 清掉）

  - health `{ok, chef_enabled, chef_pending}`

  - `GET /api/chef/tasks`（pending 列表）
  - `POST /api/chef/tasks/:id/claim`（30 分钟内重复领取 409 `CONFLICT`）

- 联调用 `CHEF_MOCK=1`（本地默认关）：pending 满 20 秒自动出示例草稿；菜名含「失败」则出带 chef_message 的空草稿。

## v2.3.1（后端组长 2026-11-09 23:20，码驼定案）——覆盖上文冲突处
### 照片大小与存储
1. **单张照片上限改为 1MB**（1,048,576 字节，后端常量 `MAX_PHOTO_BYTES`），超过返回 413 `TOO_LARGE`；正好 1,048,576 字节可以。原 10MB 作废。
2. **前端上传前先压缩**：建议长边缩到 1600px 左右、JPEG/WebP 质量 0.8，压到 1MB 以内再传（大王手机原图常有 3–8MB）。后端不做压缩，超限直接 413。
3. **`PHOTO_STORE` 环境变量**选照片存储：`kv`（默认，码驼定案）| `d1` | `r2`（备选，默认配置不含 R2 绑定，本地需 `wrangler dev --env r2`；上线默认不需要开通 R2）。接口和照片 URL 不受影响（仍是 `/api/photos/<key>`）。对比和免费额度见 `docs/照片存储方案.md`。`/api/health` 增加 `photo_store` 字段（前端可忽略）。
4. **旧字段 `photo` 作废**：multipart 里出现 `photo` 字段直接 400 `VALIDATION`，只认 `photos`（可重复）。
5. EXIF（含拍摄地点）由前端压缩时去掉，后端不处理。

### 存储写入额度 `STORAGE_QUOTA`
6. 新错误码 `STORAGE_QUOTA` **429**，message 固定「今天食堂的照片柜塞满啦，明天再来传吧～」。**真实计数**：D1 表 `kv_usage(day, ops)` 按 UTC 日期（与 Cloudflare 免费额度 00:00 UTC 重置对齐）记录每次 KV `put` 和 `delete`；上限 `KV_DAILY_WRITE_LIMIT`（默认 1000，本地可在 `.dev.vars` 调到 5 测试）。上传新菜、追加照片在写入前预判：今天已用 + 本次张数 > 上限 → 429，一张都不写。KV 自己报的额度/限流错误也统一映射为 429（依据：KV 免费版每天写入、删除各 1,000 次，超出后该类操作报错；同键每秒 1 次写入，超出 429）。后端把写入和删除合并计数，比官方更保守。
7. 新错误码 `STORAGE_FULL` **507**，message 固定「照片柜满啦，删掉一些旧照片才能继续上传～」。容量上限固定 **996,147,200 字节**（950MB，1024 进制；KV 免费版总容量 1 GB 留余量），只有本地可用 `STORAGE_LIMIT_BYTES` 临时调低（见第 22 条）。已用量 = `SUM(dish_photos.size)` + `SUM(orphan_photos.size)`（还没从 KV 真正删掉的也算）。**只有「已用 + 本次总字节 > 上限」才返回 507**，与第 23 条的 `level` 无关。
   **写照片前的校验顺序**：先容量（已用 + 本次总字节 > 上限 → 507），再每天次数（→ 429），都在写入之前，不留半条。**删除操作不受 507 限制。**
7b. **不写一半**：校验通过后先把全部照片写进存储，全部成功后才一次性写 D1（batch）；中途失败会尽力删掉已写入的照片，D1 里不留半条菜。
8. **删除**：删菜/删照片时 D1 照常删除，用户照常看到成功；存储删除如果失败（含删除额度用完），把键和字节数记进 `orphan_photos` 表，之后有任何 `/api/kitchen/*` 写入请求时后台顺手重试清理（清掉后已用量才扣回）。孤儿照片不对外提供（`/api/photos/:key` 只给 dish_photos 里登记的照片）。
9. 浏览（所有 GET）不受写入额度影响。
10. **`GET /api/kitchen/storage`**（需登录，定稿，旧的平铺字段全部作废）→
   ```json
   {
     "store": "kv",
     "photo_count": 10,
     "capacity": { "used_bytes": 2335552, "limit_bytes": 996147200, "percent": 0.2, "level": "ok", "photos_left": 1941 },
     "daily_ops": { "used": 0, "limit": 1000 }
   }
   ```
   - `store` 同 `/api/health` 的 `photo_store`；`photo_count` 来自 dish_photos。
   - `capacity.percent = used_bytes / limit_bytes × 100`，四舍五入保留 1 位小数，**只用于显示**。 JSON 数字不保留末尾的 0（80.0 会变成 `80`），前端显示时用 `percent.toFixed(1)`。
   - `capacity.level`：`ok` | `warn` | `danger`，规则见第 23 条。
   - `capacity.photos_left`：公式见第 24 条。
   - `daily_ops.used`：今天（UTC）KV put+delete 已用次数；`daily_ops.limit`：`KV_DAILY_WRITE_LIMIT`（默认 1000）。只有 `store=kv` 时才按它拦截（429）。

### 需求文档 §12 的 7 条（码驼采纳，2026-11-09）
12. **PATCH**：只改 `name/category/note`，或只做照片操作（追加/删除/排序）→ `source`、`chef_status` 不变，不作废任务。只要改了 `ingredients/steps/tips/servings/total_time` 任何一项 → `source=manual`、`chef_status=confirmed`，作废未处理的厨驼任务（清 draft、requested_note）。手写内容宽松校验（允许全空，步骤最多 30 步）。
13. **ask-chef**：对 draft 状态调用时立即丢掉草稿、置 pending（旧正式内容保留）。`requested_note` 在 confirm、discard-draft、手写保存（PATCH 内容字段）之后都清空。
14. **discard-draft**：只接受 draft 状态，其余（pending/confirmed）一律 409 `BAD_STATE`，状态不变。
15. **合法草稿只有两种**，其余一律 400 `VALIDATION`：① 食材 ≥1 条（每条 name、amount 都非空，amount 不能是空串或全空格）且步骤 3–12 步（每步 text 非空）；② 食材和步骤都是空数组且 `chef_message` 非空。caption 超 12 字截断。**confirm 合并大王修改后的结果走同一套严格校验**（13 步 → 400）；空草稿不能直接 confirm。
16. **chef_enabled=false**：厨驼的 `GET /api/chef/tasks`、`claim`、`draft` 一律 403 `CHEF_DISABLED`；大王侧 `mode=chef` 上传和 `ask-chef` 也 403；已有 pending 保留不动；已交上来的草稿照常可以 confirm / discard-draft。（厨驼读图接口不受影响。）
17. **照片数量与大小**：每道菜 1–9 张，超过 9 张（含追加后超过）400 `VALIDATION`；批量上传只要有一张不合格就整单拒绝，message 写明“第 N 张”；单张上限 1,048,576 字节，超过 413 `TOO_LARGE`，message 格式见第 25 条。
18. **Access JWT 验签单元测试**：`worker/test-unit/access-jwt.test.mts`（`npm run test:unit`）。放 `test-unit/` 而非 `test/unit/`，因为 `test/` 是后端工程师正在用、未提交的目录。iss 必须与 `ACCESS_TEAM_DOMAIN` 完全一致（不按后缀匹配）。
19. **固定值补充**：`GET /api/kitchen/storage` 的 `store` 与 `/api/health` 的 `photo_store` 始终相同（同一个 `PHOTO_STORE`）；507 `STORAGE_FULL` 文案固定「照片柜满啦，删掉一些旧照片才能继续上传～」；429 `STORAGE_QUOTA` 文案固定「今天食堂的照片柜塞满啦，明天再来传吧～」。
20. **D1 查询数**：Workers 免费版每次请求最多 50 次 D1 查询，后端 KV 次数按整批预判/记账（一次上传 9 张约 10 次 D1 查询），孤儿重试每次最多 20 个且不超过当天剩余 KV 次数。
21. **口径（码驼定，覆盖上文）**：容量一律 1024 进制——950MB = 996,147,200 字节，500KB = 512,000 字节。一次请求同时超容量和当天次数时**先判 507 再判 429**。
22. **本地开关 `STORAGE_LIMIT_BYTES`、`STORAGE_USED_SIM`**：**只在本地生效**，是否本地与 `DEV_AUTH` 用同一个判断（后端 `isLocalEnv()`：`ACCESS_TEAM_DOMAIN` 和 `ACCESS_AUD` 都没配 = 本地；配了任意一个 = 线上）。**线上就算配了这两个变量也不生效，容量上限固定 996,147,200。**
   - `STORAGE_USED_SIM=<字节数>`：把已用量模拟成该值（测 warn/danger/507 用，不用真塞照片）。
   - `STORAGE_LIMIT_BYTES=<字节数>`：临时调低容量上限。
   - 单元测试 `worker/test-unit/storage-usage.test.mts` 覆盖：线上配置下即使设了这两个变量（以及 DEV_AUTH）也被忽略。
23. **`capacity.level` 按实际字节判断，不用四舍五入后的 percent**：
   - `warn`：`used_bytes × 100 ≥ limit_bytes × 80`
   - `danger`：`used_bytes × 100 ≥ limit_bytes × 95`
   - 其余为 `ok`。
   - 例：`limit_bytes=10000`、`used_bytes=7996`（79.96%）→ `percent` 显示 `80.0`，但 `level` 仍是 `ok`。
   - **`danger` 不等于 `STORAGE_FULL`**：`danger` 只用来显示红色提醒，照样可以上传；只有「已用 + 本次 > 上限」才返回 507 `STORAGE_FULL`。
24. **剩余张数** `photos_left = floor(max(0, limit_bytes − used_bytes) / 512000)`（每张按 500KB = 512,000 字节估算）。例：`used_bytes=2,335,552`、`limit_bytes=996,147,200` → `floor(993,811,648 / 512,000)` = **1941** 张；已用 ≥ 上限时为 0。
25. **413 `TOO_LARGE` 文案**：「照片太大了（1,030KB），上限 1,024KB」。KB = `ceil(字节数 / 1024)`，千分位逗号。批量上传时前面加第几张：「第 2 张照片太大了（1,025KB），上限 1,024KB」（1,048,577 字节）。
