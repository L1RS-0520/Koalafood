# 考拉食堂 · 接口约定 v2.3.3（当前有效版）

日期：2026-11-10　维护：羊驼后端组长　依据：`worker/src/` 实际代码（逐条核对过 `index.ts`、`lib.ts`、`db.ts`、`auth.ts`、`generator/draft.ts`、`storage/usage.ts`）
**本文从开头到「变更记录」之前是唯一准绳。** 文末「变更记录」保留 v1 → v2.3.3 的历史原文，只供追溯，和上文冲突时以上文为准。

## 0. 通用约定
- 前缀 `/api`；JSON 用 UTF-8；字段名小写下划线；时间为 ISO 8601（UTC）。
- 成功：200（新建菜品为 201），直接返回数据对象。
- 失败：`{"error":{"code":"…","message":"给大王看的中文提示","details":["…"]}}`。`details` 只在校验类错误时出现，是数组：元素一般是中文字符串；v2.3.3 起能定位到某一项的问题给对象 `{"field":"steps|ingredients|tips","index":3,"reason":"only_number","message":"第 3 步只写了编号，补上做法或删掉这一步"}`，`index` 从 1 开始，与文案「第 N 步/项/条」一致。所有 `/api/*` 响应都带 `X-Content-Type-Options: nosniff`（v2.3.3）。前端直接显示 `message`；429/507 用固定文案（见 §2）。
- 本地联调：`worker/` 里 `npm run dev`（8787）。Worker 同时托管 `../web/dist`（SPA 回退），`/api/*` 先进 Worker。
- CORS（v2.3.3）：**不发任何 CORS 头**。线上同源（Worker 托管前端）；本地前端 vite dev（5173）/ preview（4173）把 `/api` 代理到后端（`web/vite.config.ts`），前端只用相对路径 `/api…`，浏览器看到的也是同源。以前「`Access-Control-Allow-Origin: *` + `Allow-Credentials: true`」的组合已去掉；任何 Origin（含陌生来源）都拿不到 ACAO。
- 未知路径：404 `NOT_FOUND`「没有这个接口」。

### 权限三种
| 标记 | 含义 |
|---|---|
| 公开 | 不用登录 |
| 登录 | 大王登录：线上 Cloudflare Access JWT（请求头 `Cf-Access-Jwt-Assertion` 或 cookie `CF_Authorization`）；本地 `DEV_AUTH=1` 时用 `/api/dev/login` 种的 `koala_dev_auth=1` cookie。未登录 401 |
| 厨驼 | 请求头 `X-Chef-Key` = `CHEF_KEY`（常量时间比较），不走 Access。错/缺 401 |

## 2. 错误码总表
| code | HTTP | 中文文案（`message`） | 触发条件 |
|---|---|---|---|
| `VALIDATION` | 400 | 按情况，例如「请填写菜名」「菜名最多 30 个字，现在是 N 个字」「请选择分类」「分类只能是：…」「备注最多 200 个字…」「请至少上传 1 张菜品照片」「照片最多 9 张，这次最多还能传 N 张」「每道菜最多 9 张照片，已经满了」「每道菜至少要留 1 张照片」「照片字段名已改为 photos（可重复），请不要再用 photo」「照片是空文件，请重新选择」「mode 只能是 chef（找厨驼写）或 manual（自己写）」「请求内容不是合法的 JSON」「ids 必须正好包含这道菜的全部照片 id，各一次」「chef_enabled 必须是 true 或 false」「草稿没通过校验：…」「确认后的菜谱不合格：…」「草稿是空的，不能直接确认…」「第 3 步只写了编号，补上做法或删掉这一步」「第 2 项食材只写了编号，补上食材名或删掉这一项」「第 1 条小贴士只写了编号，补上内容或删掉这一条」「份量（servings）最多 20 个字，现在 N 个字」「总时长（total_time）最多 20 个字，现在 N 个字」「chef_message 必须是字符串」 | 参数、表单、JSON、草稿不合规则；`servings`/`total_time` 补单位后超过 20 字（v2.3.3，不再截断）；`chef_message` 不是字符串（数字也算，v2.3.3）；步骤 / 食材名 / 小贴士去掉编号后为空（只写了「第三步」「1.」等，v2.3.3，手写、PATCH、confirm、厨驼交稿同一套，`details` 带 `{field, index, reason:"only_number", message}`）；批量照片里有一张不合格时 message 前加「第 N 张照片：」 |
| `UNAUTHORIZED` | 401 | 「请先登录考拉食堂再操作」/「厨驼密钥不对（X-Chef-Key）」/「服务器没有配置 CHEF_KEY，请先运行 worker/scripts/init-dev-vars」 | 没登录访问 `/api/kitchen/*`；厨驼密钥缺失或不对；服务器没配 CHEF_KEY |
| `CHEF_DISABLED` | 403 | 「厨驼已在设置里关闭，请先打开或改为自己写」（上传 mode=chef）/「厨驼已在设置里关闭，请先打开」（ask-chef）/「厨驼已在设置里关闭，暂时不接新任务」（厨驼 tasks/claim/draft） | `chef_enabled=false` |
| `NOT_FOUND` | 404 | 「这道菜不存在，可能已经被删除了」/「这张照片不存在」/「照片不存在」/「没有这个接口」 | 菜、照片不存在；路径不存在；dev 登录在线上或没开 DEV_AUTH |
| `CONFLICT` | 409 | 「这道菜在 <时间> 已被领取，30 分钟内不能重复领取」 | 厨驼 claim 时上次领取还没超过 `CHEF_CLAIM_TTL_MIN`（默认 30 分钟）；并发 claim 同一道菜时只有一个成功，其余也是这个错误（v2.3.3） |
| `BAD_STATE` | 409 | 「这道菜现在没有待确认的厨驼草稿」（confirm）/「…不能放弃」（discard-draft）/「这道菜不在待写状态，不能领取」（claim）/「这道菜现在是 X 状态，只有 pending（待写）的菜能交稿」/「这道菜刚刚被改了状态，交稿没写进去…」/「这道菜的草稿刚刚被改了…没有确认…」（confirm）/「这道菜刚刚被改了状态，没有待确认的厨驼草稿可放弃…」（discard-draft） | confirm、discard-draft 时不是 draft；claim、交稿时不是 pending；交稿、confirm、discard-draft 时状态被同时改掉（v2.3.3 起 confirm / discard-draft 也是原子写入） |
| `TOO_LARGE` | 413 | 「照片太大了（1,030KB），上限 1,024KB」；批量时「第 2 张照片太大了（1,025KB），上限 1,024KB」；JSON 请求体：「内容太大了（65KB），上限 64KB」 | 单张 > 1,048,576 字节。KB = ceil(字节/1024)，千分位逗号；厨驼交稿、PATCH 菜品、confirm 的 JSON 请求体 > 65,536 字节（64KB，v2.3.3）：先看 Content-Length，没有就按实际读到的字节数；KB 同样 ceil(字节/1024)、千分位 |
| `BAD_TYPE` | 415 | 「照片格式不支持，只能上传 jpg、png 或 webp 图片」（批量时前加「第 N 张照片：」） | 文件头不是 JPEG/PNG/WebP（按 magic bytes，不看扩展名和 MIME） |
| `STORAGE_QUOTA` | 429 | **固定**「今天食堂的照片柜塞满啦，明天再来传吧～」 | 照片存 KV 时，今天（UTC）已用次数 + 本次张数 > `KV_DAILY_WRITE_LIMIT`；或 KV 自己报额度/限流错误 |
| `INTERNAL` | 500 | 「服务器开小差了，请稍后再试」 | 未预料的错误 |
| `STORAGE_FULL` | 507 | **固定**「照片柜满啦，删掉一些旧照片才能继续上传～」 | 已用字节 + 本次总字节 > 上限 996,147,200 |

两个都超时**先判 507 再判 429**；两者都在写任何照片之前判断，被拦时一张都不写、不留半条菜。

## 3. 数据对象
### 3.1 Dish（详情 / 写操作的返回）
```json
{
  "id": "uuid", "name": "番茄炒蛋", "category": "家常菜", "note": "少放糖",
  "photo_url": "/api/photos/<key>",
  "photos": [{"id": "uuid", "url": "/api/photos/<key>"}],
  "ingredients": [{"name": "鸡蛋", "amount": "3个"}],
  "steps": [{"text": "…", "heat": "中火", "time": "30秒", "caption": "打散它！"}],
  "tips": ["…"], "servings": "2人份", "total_time": "15分钟",
  "source": "chef", "chef_status": "confirmed",
  "draft": null, "requested_note": null, "chef_requested_at": null,
  "created_at": "…", "updated_at": "…"
}
```
- `photos` 按顺序，第一张是封面；`photo_url` = 封面（没有照片时 null）。
- 顶层 `ingredients/steps/tips/servings/total_time` 永远是**已确认的正式内容**；pending/draft 期间旧正式内容照常显示，从没确认过就是空数组 / null。
- `draft`：只在 `chef_status=draft` 且已登录时有值，`{ingredients, steps, tips, servings, total_time, chef_message}`；其余情况 null。
- `requested_note`：大王给厨驼的要求；未登录时为 null。
- `source`：`chef | manual`，正式内容来源。

### 3.2 DishSummary（列表）
`{id, name, category, photo_url, photo_count, source, chef_status, total_time, created_at}`
- `total_time`（v2.3.2）：字符串或 null，不登录也返回；与 Dish 顶层 `total_time` 同一口径，只给已确认的值，草稿里的时长不进列表。

### 3.3 Task（厨驼）
`{id, name, category, note, requested_note, photos:[{id, url:"/api/chef/tasks/<id>/photos/<photoId>"}], requested_at, claimed_at}`

### 3.4 health
`{ok:true, chef_enabled, chef_pending（pending 数）, chef_mock（CHEF_MOCK 是否开）, photo_store（kv|d1|r2）, orphan_photos（待清理的照片数）}`

### 3.5 Storage（`GET /api/kitchen/storage`）
```json
{
  "store": "kv",
  "photo_count": 10,
  "capacity": {"used_bytes": 2335552, "limit_bytes": 996147200, "percent": 0.2, "level": "ok", "photos_left": 1941},
  "daily_ops": {"used": 0, "limit": 1000}
}
```
- `store` 始终等于 health 的 `photo_store`；`photo_count` 来自 dish_photos。
- `used_bytes` = SUM(dish_photos.size) + SUM(orphan_photos.size)。
- `percent` = used/limit×100，四舍五入 1 位小数，**只做显示**；JSON 数字不带末尾 0（80.0 是 `80`），前端用 `percent.toFixed(1)` 显示。
- `level` 按**字节**判断：`used_bytes×100 ≥ limit_bytes×95` → `danger`；`≥ limit_bytes×80` → `warn`；其余 `ok`。例：limit 10000、used 7996（79.96%）→ percent 显示 80.0，level 仍是 `ok`。
- **`danger` 不等于 `STORAGE_FULL`**：danger 只显示红色提醒，照样能上传；只有「已用 + 本次 > 上限」才 507。
- `photos_left = floor(max(0, limit_bytes − used_bytes) / 512000)`（每张按 500KB = 512,000 字节估算）。例：used 2,335,552 → floor(993,811,648/512,000) = 1941。
- `daily_ops.used`：今天（UTC）KV put+delete 次数；`daily_ops.limit` = `KV_DAILY_WRITE_LIMIT`（默认 1000）。不管哪种存储都返回，但**只有 `store=kv` 时才按它拦 429**。
- 旧的平铺字段（`used_bytes` 在顶层、`used_pct`、`ops_today`、`ops_limit`、`ops_pct`、`warn`）已删除。`GET /api/settings` 不带用量。

## 4. 规则（当前有效）
### 4.1 状态
- `chef_status`：`pending`（等厨驼写）| `draft`（厨驼已交稿，等大王确认）| `confirmed`（正式）。
- 上传：`mode=chef` → pending、source=chef、内容为空；`mode=manual`（默认）→ confirmed、source=manual。
- `ask-chef`：任何状态都可调用 → pending；丢掉已有草稿、清掉领取记录，`note` 存进 `requested_note`；旧正式内容保留。
- `confirm`：只对 draft；把大王修改（可选）合并到草稿上，**按厨驼交稿同一套严格规则再校验**（§4.4①），通过后 → confirmed、source=chef，清 draft、requested_note。食材和步骤都空的草稿不能直接 confirm（400）。
- `discard-draft`：只对 draft，否则 409 BAD_STATE；→ confirmed，正式内容不变，清 draft、requested_note、chef_requested_at。
- `PATCH`：只改 `name/category/note` 或只做照片操作 → source、chef_status 不变；**只要请求里出现** `ingredients/steps/tips/servings/total_time` 任何一个键（哪怕值没变）→ source=manual、chef_status=confirmed，作废未处理的厨驼任务（清 draft、requested_note、claimed_at、chef_requested_at）。手写内容宽松校验（§4.4②）。
- `chef_enabled=false`：上传 mode=chef、ask-chef、厨驼 tasks/claim/draft 都 403；已有 pending 保留；已交的草稿照常 confirm / discard-draft；厨驼读图不受影响。

### 4.2 字段长度
- 菜名必填，≤30 字（按字符数）；分类只能是 6 个之一；备注 ≤200 字，空白当 null。
- `servings`、`total_time`：字符串 ≤20 字，**超出返回 400 VALIDATION**（v2.3.3，交稿 / 手写上传 / PATCH / confirm 合并后的最终值都查）；给数字时先自动补单位（2 → "2人份"，15 → "15分钟"）再量长度；空串当 null。

### 4.3 照片
- 字段名 `photos`（可重复）；出现旧字段 `photo` 直接 400。空串项忽略。
- 每道菜 1–9 张；追加后超 9 张 400；只剩 1 张时不能删（400）。
- 单张 ≤1,048,576 字节（413）；只认 JPEG/PNG/WebP 文件头（415）。批量里有一张不合格整单拒绝，message 写第几张。前端上传前压缩（建议长边 1600px、质量 0.8）并去掉 EXIF，后端不压缩。
- 顺序：`PUT …/photos/order` 的 `ids` 必须正好是这道菜全部照片 id，各一次。
- 写入顺序：先预判 507/429 → 写全部照片到存储 → 一次性写 D1；中途失败尽力删掉已写的照片，不留半条菜。
- 删除：D1 照常删、照常返回成功；存储删不掉的（含当天次数用完）记进 `orphan_photos`，之后每次 `/api/kitchen/*` 请求结束后后台重试（每次最多 20 个，不超过当天剩余次数），清掉后已用量才扣回。孤儿照片不再对外提供。
- `PHOTO_STORE`：`kv`（默认）| `d1` | `r2`（只在 `wrangler dev --env r2` 下可用）；照片 URL 都是 `/api/photos/<key>`。
- 浏览（所有 GET）不受容量和次数限制。

### 4.4 草稿校验（`normalizeDraft`）
① **厨驼交稿 / confirm 合并后（严格）**，合法的只有两种：
  - 食材 ≥1 项（每项 name、amount 都非空）且步骤 3–12 步（每步 text 非空）；
  - 食材、步骤都是空数组且 `chef_message` 非空（“写不了”）。
② **手写 / PATCH（宽松）**：允许全空；步骤最多 30 步；amount 可空。
共同规则：食材最多 40 项（超出 400）；食材名、用量各 ≤20 字（截断）；步骤 text ≤300 字（超出 400，请拆步）；步骤开头编号（“1.”“第一步：”“步骤2”“Step 3:”）自动去掉，**去掉后为空（只写了编号）返回 400**，食材名、小贴士同样（v2.3.3）；`heat` 规范别名（旺火/猛火/武火→大火，文火→小火，“无”→空）、≤8 字截断；`time` ≤12 字截断；`caption` ≤12 字截断；小贴士最多 10 条（多的丢弃）、每条 ≤120 字截断；`chef_message` ≤200 字截断。食材也可写成字符串“鸡蛋 3个”/“鸡蛋：3个”。截断记进交稿响应的 `warnings`。

### 4.5 厨驼
- `GET /api/chef/tasks`：只列 pending，按 chef_requested_at、created_at 正序。
- `claim`：只对 pending（否则 409 BAD_STATE）；上次领取 30 分钟内再领 409 CONFLICT，超时可重领。
- `draft`：只对 pending；通过校验 → draft，清领取记录。
- `CHEF_MOCK=1`（只用于联调，默认关）：pending 满 20 秒的菜在下次读取 health/列表/详情/tasks 时自动写成示例草稿；菜名含「失败」时出带 chef_message 的空草稿。

### 4.6 登录与隐私
- 是否本地由 `isLocalEnv()` 判断：`ACCESS_TEAM_DOMAIN` 和 `ACCESS_AUD` 都没配 = 本地；配了任意一个 = 线上。
- 线上：Access JWT（RS256，JWKS `https://<team>/cdn-cgi/access/certs`），iss 必须与团队域名完全一致、aud 含 `ACCESS_AUD`、未过期；只配了一半时任何人都登录不了（关死）。
- 本地：`DEV_AUTH=1` 时 `/api/dev/login|logout` 可用；线上或没开时 404。
- 未登录：Dish 的 `draft`、`requested_note`、`chef_requested_at`（v2.3.3）为 null（`chef_status` 照常返回）；列表不含草稿内容，也不含 `chef_requested_at`。登录后照常返回。

### 4.7 容量与次数
- 容量上限线上固定 996,147,200 字节（950MB，1024 进制）。次数上限 `KV_DAILY_WRITE_LIMIT`（默认 1000，put 和 delete 合并计，UTC 零点重置）。
- **本地开关** `STORAGE_LIMIT_BYTES`（调低上限）、`STORAGE_USED_SIM`（模拟已用字节）只在本地生效，线上配了也不读；单元测试覆盖。

#### 存储写入额度 `STORAGE_QUOTA`
6. 新错误码 `STORAGE_QUOTA` **429**，message 固定「今天食堂的照片柜塞满啦，明天再来传吧～」。**真实计数**：D1 表 `kv_usage(day, ops)` 按 UTC 日期（与 Cloudflare 免费额度 00:00 UTC 重置对齐）记录每次 KV `put` 和 `delete`；上限 `KV_DAILY_WRITE_LIMIT`（默认 1000，本地可在 `.dev.vars` 调到 5 测试）。上传新菜、追加照片在写入前预判：今天已用 + 本次张数 > 上限 → 429，一张都不写。KV 自己报的额度/限流错误也统一映射为 429（依据：KV 免费版每天写入、删除各 1,000 次，超出后该类操作报错；同键每秒 1 次写入，超出 429）。后端把写入和删除合并计数，比官方更保守。
7. 新错误码 `STORAGE_FULL` **507**，message 固定「照片柜满啦，删掉一些旧照片才能继续上传～」。容量上限固定 **996,147,200 字节**（950MB，1024 进制；KV 免费版总容量 1 GB 留余量），只有本地可用 `STORAGE_LIMIT_BYTES` 临时调低（见第 22 条）。已用量 = `SUM(dish_photos.size)` + `SUM(orphan_photos.size)`（还没从 KV 真正删掉的也算）。**只有「已用 + 本次总字节 > 上限」才返回 507**，与第 23 条的 `level` 无关。
   **写照片前的校验顺序**：先容量（已用 + 本次总字节 > 上限 → 507），再每天次数（→ 429），都在写入之前，不留半条。**删除操作不受 507 限制。**
7b. **不写一半**：校验通过后先把全部照片写进存储，全部成功后才一次性写 D1（batch）；中途失败会尽力删掉已写入的照片，D1 里不留半条菜。
8. **删除**：删菜/删照片时 D1 照常删除，用户照常看到成功；存储删除如果失败（含删除额度用完），把键和字节数记进 `orphan_photos` 表，之后有任何 `/api/kitchen/*` 写入请求时后台顺手重试清理（清掉后已用量才扣回）。孤儿照片不对外提供（`/api/photos/:key` 只给 dish_photos 里登记的照片）。
9. 浏览（所有 GET）不受写入额度影响。
10. **`GET /api/kitchen/storage`**（需登录，定稿，旧的平铺字段全部作废）→
   ```json
   {
     "store": "kv",
     "photo_count": 10,
     "capacity": { "used_bytes": 2335552, "limit_bytes": 996147200, "percent": 0.2, "level": "ok", "photos_left": 1941 },
     "daily_ops": { "used": 0, "limit": 1000 }
   }
   ```
   - `store` 同 `/api/health` 的 `photo_store`；`photo_count` 来自 dish_photos。
   - `capacity.percent = used_bytes / limit_bytes × 100`，四舍五入保留 1 位小数，**只用于显示**。 JSON 数字不保留末尾的 0（80.0 会变成 `80`），前端显示时用 `percent.toFixed(1)`。
   - `capacity.level`：`ok` | `warn` | `danger`，规则见第 23 条。
   - `capacity.photos_left`：公式见第 24 条。
   - `daily_ops.used`：今天（UTC）KV put+delete 已用次数；`daily_ops.limit`：`KV_DAILY_WRITE_LIMIT`（默认 1000）。只有 `store=kv` 时才按它拦截（429）。
   - `GET /api/settings` 不带用量字段。

#### 需求文档 §12 的 7 条（码驼采纳，2026-11-09）
12. **PATCH**：只改 `name/category/note`，或只做照片操作（追加/删除/排序）→ `source`、`chef_status` 不变，不作废任务。只要改了 `ingredients/steps/tips/servings/total_time` 任何一项 → `source=manual`、`chef_status=confirmed`，作废未处理的厨驼任务（清 draft、requested_note）。手写内容宽松校验（允许全空，步骤最多 30 步）。
13. **ask-chef**：对 draft 状态调用时立即丢掉草稿、置 pending（旧正式内容保留）。`requested_note` 在 confirm、discard-draft、手写保存（PATCH 内容字段）之后都清空。
14. **discard-draft**：只接受 draft 状态，其余（pending/confirmed）一律 409 `BAD_STATE`，状态不变。
15. **合法草稿只有两种**，其余一律 400 `VALIDATION`：① 食材 ≥1 条（每条 name、amount 都非空，amount 不能是空串或全空格）且步骤 3–12 步（每步 text 非空）；② 食材和步骤都是空数组且 `chef_message` 非空。caption 超 12 字截断。**confirm 合并大王修改后的结果走同一套严格校验**（13 步 → 400）；空草稿不能直接 confirm。
16. **chef_enabled=false**：厨驼的 `GET /api/chef/tasks`、`claim`、`draft` 一律 403 `CHEF_DISABLED`；大王侧 `mode=chef` 上传和 `ask-chef` 也 403；已有 pending 保留不动；已交上来的草稿照常可以 confirm / discard-draft。（厨驼读图接口不受影响。）
17. **照片数量与大小**：每道菜 1–9 张，超过 9 张（含追加后超过）400 `VALIDATION`；批量上传只要有一张不合格就整单拒绝，message 写明“第 N 张”；单张上限 1,048,576 字节，超过 413 `TOO_LARGE`，message 格式见第 25 条。
18. **Access JWT 验签单元测试**：`worker/test-unit/access-jwt.test.mts`（`npm run test:unit`）。放 `test-unit/` 而非 `test/unit/`，因为 `test/` 是后端工程师正在用、未提交的目录。iss 必须与 `ACCESS_TEAM_DOMAIN` 完全一致（不按后缀匹配）。
19. **固定值补充**：`GET /api/kitchen/storage` 的 `store` 与 `/api/health` 的 `photo_store` 始终相同（同一个 `PHOTO_STORE`）；507 `STORAGE_FULL` 文案固定「照片柜满啦，删掉一些旧照片才能继续上传～」；429 `STORAGE_QUOTA` 文案固定「今天食堂的照片柜塞满啦，明天再来传吧～」。
20. **D1 查询数**：Workers 免费版每次请求最多 50 次 D1 查询，后端 KV 次数按整批预判/记账（一次上传 9 张约 10 次 D1 查询），孤儿重试每次最多 20 个且不超过当天剩余 KV 次数。
21. **口径（码驼定，覆盖上文）**：容量一律 1024 进制——950MB = 996,147,200 字节，500KB = 512,000 字节。一次请求同时超容量和当天次数时**先判 507 再判 429**。
22. **本地开关 `STORAGE_LIMIT_BYTES`、`STORAGE_USED_SIM`**：**只在本地生效**，是否本地与 `DEV_AUTH` 用同一个判断（后端 `isLocalEnv()`：`ACCESS_TEAM_DOMAIN` 和 `ACCESS_AUD` 都没配 = 本地；配了任意一个 = 线上）。**线上就算配了这两个变量也不生效，容量上限固定 996,147,200。**
   - `STORAGE_USED_SIM=<字节数>`：把已用量模拟成该值（测 warn/danger/507 用，不用真塞照片）。
   - `STORAGE_LIMIT_BYTES=<字节数>`：临时调低容量上限。
   - 单元测试 `worker/test-unit/storage-usage.test.mts` 覆盖：线上配置下即使设了这两个变量（以及 DEV_AUTH）也被忽略。
23. **`capacity.level` 按实际字节判断，不用四舍五入后的 percent**：
   - `warn`：`used_bytes × 100 ≥ limit_bytes × 80`
   - `danger`：`used_bytes × 100 ≥ limit_bytes × 95`
   - 其余为 `ok`。
   - 例：`limit_bytes=10000`、`used_bytes=7996`（79.96%）→ `percent` 显示 `80.0`，但 `level` 仍是 `ok`。
   - **`danger` 不等于 `STORAGE_FULL`**：`danger` 只用来显示红色提醒，照样可以上传；只有「已用 + 本次 > 上限」才返回 507 `STORAGE_FULL`。
24. **剩余张数** `photos_left = floor(max(0, limit_bytes − used_bytes) / 512000)`（每张按 500KB = 512,000 字节估算）。例：`used_bytes=2,335,552`、`limit_bytes=996,147,200` → `floor(993,811,648 / 512,000)` = **1941** 张；已用 ≥ 上限时为 0。
25. **413 `TOO_LARGE` 文案**：「照片太大了（1,030KB），上限 1,024KB」。KB = `ceil(字节数 / 1024)`，千分位逗号。批量上传时前面加第几张：「第 2 张照片太大了（1,025KB），上限 1,024KB」（1,048,577 字节）。

### v2.3.3（后端组长 2026-11-10，CTO 定案）
27. **`servings`、`total_time` 超过 20 字返回 400 `VALIDATION`**，不再静默截断。厨驼交稿、手写上传、PATCH、confirm 都查；confirm 查的是合并后的最终值（含从草稿继承的）。给数字时仍先自动补单位（`3` → "3人份"），补完再量长度。文案点名字段和上限，例如「份量（servings）最多 20 个字，现在 21 个字」「总时长（total_time）最多 20 个字，现在 21 个字」。
28. **claim 并发修复**：领取改为原子写入（`WHERE id=? AND chef_status='pending' AND (claimed_at IS NULL OR claimed_at < 过期点)` 并检查写入行数）。同一道菜并发 claim 只有一个 200，其余返回已有的 409 `CONFLICT`（「这道菜在 <时间> 已被领取…」）；这期间状态已不是 pending 的返回 409 `BAD_STATE`。没 claim 直接交稿仍然允许。confirm、discard-draft 同样改为原子写入（只对此刻仍是 draft 的那份草稿生效），并发冲突时返回 409 `BAD_STATE`。
29. **`chef_message` 只收字符串**：数字、对象、数组一律 400 `VALIDATION`（「chef_message 必须是字符串」）。
30. **`chef_requested_at` 对访客隐藏**：未登录的详情返回 null（与 `draft`、`requested_note` 同口径），列表不含该字段；登录后照常返回。
31. **安全头与 CORS（QA R1-06）**：所有 `/api/*` 响应（含错误、404、照片 `/api/photos/*`）带 `X-Content-Type-Options: nosniff`。不再发 CORS 头：线上同源；本地前端 vite dev/preview 通过代理访问 `/api`（`web/vite.config.ts`），前端只用相对路径，也是同源。原来「ACAO * + Allow-Credentials true」的组合去掉，任何 Origin 都拿不到 ACAO。
32. **只写了编号（QA R1-07）**：步骤去掉编号后为空（“第三步”“1.”“Step 3:”）返回 400 `VALIDATION`，文案「第 3 步只写了编号，补上做法或删掉这一步」；食材名「第 N 项食材只写了编号，补上食材名或删掉这一项」、小贴士「第 N 条小贴士只写了编号，补上内容或删掉这一条」。`details` 里对应项是对象 `{field:"steps"|"ingredients"|"tips", index, reason:"only_number", message}`，`index` 从 1 开始、与文案序号一致。手写上传、PATCH、confirm（文案同手写）、厨驼交稿（前缀「草稿没通过校验：」）同一套校验。
33. **JSON 请求体上限（QA R1-08）**：厨驼交稿、PATCH 菜品、confirm 的请求体 > 65,536 字节返回 413 `TOO_LARGE`「内容太大了（xxKB），上限 64KB」，xx = ceil(字节/1024)（千分位）。先看 Content-Length（不读 body），没有就按实际读到的字节数。正好 65,536 字节照常处理。
